## 1. Flutter vs React Native — Quick Mental Map

| `StatefulWidget` | `React.FC` + `useState` | Local state via hooks |
| `BuildContext` | `props` / `useContext` | Pass data via props or context |

## 3. Core Layer — File by File

### 📁 `core/constants/`

#### `api_urls.ts`
**What it does:** Defines all your API endpoint URLs in one place.  
**Why:** When your base URL changes (dev → staging → live), you change it in ONE file, not everywhere.  
**Flutter equivalent:** Your `ApiUrl` enum in `core/constants/api_urls.dart`

```ts
// Usage
import { getUrl, ApiUrl } from '../constants/api_urls';

const endpoint = getUrl(ApiUrl.Homes); // returns "/homes"
```

#### `app_constants.ts`
**What it does:** All constant string keys used across the app (token key, language key, header names).  
**Why:** Avoids magic strings scattered everywhere. If a key name changes, update once.  
**Flutter equivalent:** `AppConstants` enum in Flutter

```ts
// Usage
import { AppConstants } from '../constants/app_constants';

await storage.setString(AppConstants.Token, 'abc123');
```

---

### 📁 `core/error/`

This is the **heart of clean error handling**. Same concept as Flutter's dartz package.

#### `exceptions.ts`
**What it does:** Defines specific exception types that the data layer throws.  
**Why:** Instead of generic `Error`, you throw typed exceptions so the code above knows exactly what went wrong.  
**Flutter equivalent:** `exceptions.dart` in your Flutter clean architecture

| Exception | When thrown |
|---|---|
| `ServerException` | API returned 5xx or unexpected error |
| `NetworkException` | No internet connection |
| `UnauthorizedException` | 401 / 403 — token invalid |
| `ValidationException` | 422 — form/input validation failed |
| `TooManyRequestsException` | 429 — rate limited |
| `NotFoundException` | 404 — resource not found |
| `TimeoutException` | Request took too long |

```ts
// Thrown deep inside api_client.ts
throw new UnauthorizedException('Token expired', 401);
```

#### `failures.ts`
**What it does:** Defines Failure types that the domain layer exposes.  
**Why:** The presentation layer (UI) should not know about `axios` or `http`. It only sees `Failure` objects. This is the **boundary between data and presentation**.  
**Flutter equivalent:** `failures.dart`

```ts
// Presentation layer only deals with Failure, never exceptions
if (failure instanceof ValidationFailure) {
  showAlert(failure.firstError);
}
```

#### `exception_handler.ts`
**What it does:** Provides the `Either<L, R>` type AND the `handleException()` function.  
**Why:** This is the glue. Repository implementations call `handleException()` which catches any exception and converts it to `Either<Failure, Data>`. The UI never sees a raw throw.  
**Flutter equivalent:** `exception_handler.dart` + `dartz` package

```ts
// In repository implementation
async getHomes(): Promise<Either<Failure, HomeEntity[]>> {
  return handleException(() => this.remoteDataSource.getHomes());
  //                     ↑ Any exception thrown here is caught
  //                       and returned as Left(Failure)
}

// In the store (presentation)
const result = await getHomes.call(new NoParams());
if (isRight(result)) {
  // result.value is HomeEntity[] — success path
}
if (isLeft(result)) {
  // result.value is Failure — error path
}
```

**What is `Either`?**  
A value that is either a `Left` (failure/error) OR a `Right` (success/data). Never both.  
- `Left(failure)` = something went wrong  
- `Right(data)` = everything succeeded  
This forces you to handle both cases. No silent failures.

### 📁 `core/models/`

#### `global_paginator.ts`
**What it does:** Standard pagination model (current page, total pages, records per page).  
**Why:** Every paginated API response has the same structure. Define it once.  
**Flutter equivalent:** `GlobalPaginator` class

#### `global_response.ts`
**What it does:** Standard API response wrapper (message, errors, code).  
**Why:** Your backend always returns `{ message, errors, code }`. Define it once.  
**Flutter equivalent:** `GlobalResponse` class

### 📁 `core/network/`

#### `api_client.ts`
**What it does:** The single HTTP client for all API calls. Built on Axios.  
**Why:** Centralizes all HTTP logic — auth headers, logging, error handling, timeout. No feature writes raw Axios calls.  
**Flutter equivalent:** `ApiClient` using Dio

**Key features:**
- Auto-injects `Authorization: Bearer <token>` header
- Logs every request and response
- Converts HTTP errors → typed exceptions
- Handles SSL Wireless-specific response format (`{ code, message, errors }`)

```ts
// Usage in a datasource
return this.apiClient.request<HomeModel[]>({
  endpoint: '/homes',
  method: HttpMethod.GET,
  converter: (data) => (data as []).map(homeModelFromJson),
});
```

#### `network_info.ts`
**What it does:** Checks if device is connected to the internet.  
**Why:** Before making API calls, check connectivity. Show proper "no internet" messages.  
**Flutter equivalent:** `NetworkInfo` + `connectivity_plus`

### 📁 `core/di/`

#### `service_locator.ts`
**What it does:** A simple dependency injection container (service locator pattern).  
**Why:** Components don't create their own dependencies. They ask the locator for them. Makes testing and swapping implementations easy.  
**Flutter equivalent:** `GetIt` service locator

```ts
// Register once at app startup (in App.tsx)
await initDependencies();

// Use anywhere
const getHomes = sl.get<GetHomes>('getHomes');
```

**How it works:**
1. `initDependencies()` runs once when the app starts
2. It creates all objects (`ApiClient`, repositories, use cases) and registers them
3. Anywhere in the app, `sl.get<T>('key')` returns the singleton instance

### 📁 `core/presentation/components/`

These are **global reusable UI components** — the React Native equivalent of Flutter's global widgets.

| Component | Flutter Equivalent | Purpose |
|---|---|---|
| `GlobalText.tsx` | `GlobalText` widget | Consistent text styling across app |
| `GlobalButton.tsx` | `GlobalButton` widget | Primary action button with loading state |
| `GlobalLoader.tsx` | `GlobalLoader` widget | Loading indicator with optional text |
| `GlobalInput.tsx` | `GlobalTextFormField` widget | Text input with label, error display |

**Why use these instead of raw RN components?**  
If you later want to change all buttons to use a different color or font, you change `GlobalButton` — not 50 screens.

```tsx
// Instead of this (everywhere)
<Text style={{ fontSize: 14, color: '#212121', fontWeight: '500' }}>Hello</Text>

// Use this
<GlobalText str="Hello" fontSize={14} />
```

### 📁 `core/presentation/hooks/`

#### `useErrorHandler.ts`
**What it does:** A React hook that shows an alert when a `Failure` is received.  
**Why:** Centralizes error display logic. Every screen uses the same error presentation.  
**Flutter equivalent:** `ErrorHandlerMixin`

```ts
// In any screen
const { handleFailure } = useErrorHandler();

useEffect(() => {
  if (status === 'error' && failure) {
    handleFailure(failure); // Shows Alert automatically
  }
}, [status, failure]);
```

**What is a Hook?**  
A hook is a function that starts with `use`. It lets you "hook into" React features (state, lifecycle) from a functional component. Think of it like a mixin in Flutter but for functions.

### 📁 `core/usecases/`

#### `usecase.ts`
**What it does:** Abstract base class that every use case must implement.  
**Why:** Enforces a consistent `call(params)` interface. Also provides `NoParams` for use cases that need no input.  
**Flutter equivalent:** `UseCase<Type, Params>` abstract class

```ts
// Every use case looks like this
export abstract class UseCase<T, Params> {
  abstract call(params: Params): Promise<Either<Failure, T>>;
}

export class NoParams {} // Used when no input is needed
```

### 📁 `core/utils/`

#### `preferences_helper.ts`
**What it does:** Singleton wrapper around `AsyncStorage` for typed key-value storage.  
**Why:** `AsyncStorage` is async and verbose. This gives you a clean API. Also a singleton so any class can get the same instance.  
**Flutter equivalent:** `PrefHelper` singleton using `SharedPreferences`

```ts
const prefs = PreferencesHelper.instance;

await prefs.setString(AppConstants.Token, 'abc123');
const token = await prefs.getString(AppConstants.Token); // 'abc123'
await prefs.setBool(AppConstants.IsDarkMode, true);
```

> ⚠️ **Important difference from Flutter:** AsyncStorage is **async** (returns Promises). In Flutter, SharedPreferences is sync after initialization. In RN, always `await` storage calls.

#### `validators.ts`
**What it does:** Input validation functions (email, password, phone, OTP, required).  
**Flutter equivalent:** `Validators` class

```ts
const error = Validators.email('notanemail');  // 'Please enter a valid email'
const ok    = Validators.email('a@b.com');     // null — valid
```

#### `extension.ts`
**What it does:** Utility functions for strings, arrays, and dates.  
**Why:** TypeScript doesn't support extension methods like Dart, so these are plain utility functions.  
**Flutter equivalent:** Extension files (`extension.dart`)

## 4. Feature Layer — File by File

Every feature (`homes`, `auth`, `payment`, etc.) has the same 3-layer structure.

### Layer 1 — Domain (Business Logic, Framework-Independent)

```
features/homes/domain/
  ├── entities/home.ts          ← Pure data model, no JSON parsing
  ├── repositories/home_repository.ts  ← Contract/interface (abstract)
  └── usecases/get_home.ts      ← One use case = one business action
```

#### `entities/home.ts`
**What it does:** Defines the pure business object. No JSON, no API concerns.  
**Flutter equivalent:** Entity class extending `Equatable`

```ts
export interface HomeEntity {
  id: number;
  title: string;
  // Only business-relevant fields
}
```

#### `repositories/home_repository.ts`
**What it does:** Defines WHAT the data layer can do, not HOW.  
**Flutter equivalent:** Abstract repository class

```ts
export interface HomeRepository {
  getHomes(): Promise<Either<Failure, HomeEntity[]>>;
}
// This is just a CONTRACT. The actual implementation is in data/
```

#### `usecases/get_home.ts`
**What it does:** Represents a single business action. Calls the repository.  
**Why:** Use cases are the only way the presentation layer accesses data. They enforce single responsibility.  
**Flutter equivalent:** Use case class implementing `UseCase<T, Params>`

```ts
export class GetHomes implements UseCase<HomeEntity[], NoParams> {
  constructor(private readonly repository: HomeRepository) {}

  async call(_params: NoParams): Promise<Either<Failure, HomeEntity[]>> {
    return this.repository.getHomes();
  }
}
```

### Layer 2 — Data (API Calls, Local Storage, Models)

```
features/homes/data/
  ├── datasources/
  │   ├── home_remote_datasource.ts  ← Actual API calls

  ├── models/home_model.ts           ← JSON parsing model
  └── repositories/home_repository_impl.ts  ← Implements domain contract
```

#### `models/home_model.ts`
**What it does:** Extends the entity with JSON parsing (`fromJson` / `toJson`).  
**Flutter equivalent:** Model class with `fromJson`/`toJson`

```ts
export interface HomeModel extends HomeEntity {
  // extra backend-only fields if needed
}

export function homeModelFromJson(json: Record<string, unknown>): HomeModel {
  return { id: json['id'] as number };
}
```

#### `datasources/home_remote_datasource.ts`
**What it does:** Makes the actual HTTP call using `ApiClient`.  
**Flutter equivalent:** Remote datasource implementation

```ts
export class HomeRemoteDataSourceImpl implements HomeRemoteDataSource {
  constructor(private readonly apiClient: ApiClient) {}

  async getHomes(): Promise<HomeModel[]> {
    return this.apiClient.request({
      endpoint: '/homes',

  }
}
```

#### `repositories/home_repository_impl.ts`
**What it does:** Implements the domain repository interface using data sources. Wraps calls with `handleException`.  
**Flutter equivalent:** Repository implementation

```ts
export class HomeRepositoryImpl implements HomeRepository {
  async getHomes(): Promise<Either<Failure, HomeEntity[]>> {
    return handleException(() => this.remote.getHomes());
    // If getHomes() throws any exception → returns Left(Failure)
    // If it succeeds → returns Right(HomeEntity[])
  }
}
```

### Layer 3 — Presentation (Screens, State, Components)

```
features/homes/presentation/
  ├── screens/HomeScreen.tsx      ← The full screen widget
  ├── components/HomeWidget.tsx   ← Reusable UI piece for this feature
  └── store/
      ├── home_state.ts           ← State shape definition
      └── home_store.ts           ← Zustand store (state + actions)
```

#### `store/home_state.ts`
**What it does:** Defines the shape of the state for this feature.  
**Flutter equivalent:** `HomeState` class (sealed or regular)

```ts
export type HomeStatus = 'idle' | 'loading' | 'success' | 'error';

export interface HomeState {
  status: HomeStatus;
  homes: HomeEntity[];
  failure?: Failure;
}
```

#### `store/home_store.ts`
**What it does:** The Zustand store — holds state and defines actions.  
**Flutter equivalent:** `StateNotifier` (Riverpod) or `Bloc` (BLoC pattern)

```ts
export const useHomeStore = create<HomeStore>((set) => ({
  ...initialHomeState,

  fetchHomes: async () => {
    set({ status: 'loading' });
    const result = await getHomes.call(new NoParams());
    if (isRight(result)) set({ status: 'success', homes: result.value });
    else set({ status: 'error', failure: result.value });
  },
}));
```

#### `screens/HomeScreen.tsx`
**What it does:** The actual screen. Subscribes to the store, renders UI.  
**Flutter equivalent:** A `ConsumerWidget` (Riverpod) or `BlocBuilder` screen

```tsx
const HomeScreen: React.FC = () => {
  const { status, homes, failure, fetchHomes } = useHomeStore();
  // status, homes come from Zustand store (like ref.watch in Riverpod)
  // fetchHomes is the action (like ref.read(provider.notifier).fetch())

  useEffect(() => { fetchHomes(); }, []); // like initState

  if (status === 'loading') return <GlobalLoader />;

  return <FlatList data={homes} renderItem={...} />;
};
```

## 6. State Management — Why Zustand?

### The Options (and why we picked Zustand)

As a Flutter developer who prefers **Riverpod**, here is the honest comparison of React Native state management options:

---

### Option 1 — Redux Toolkit
**Flutter equivalent:** BLoC  
**Verdict:** ❌ Not recommended for you

- Requires `actions`, `reducers`, `selectors`, `dispatch` — a lot of boilerplate
- Like BLoC but even more verbose
- Great for very large teams but overkill for most apps
- You said you prefer Riverpod over BLoC — Redux is the BLoC of React Native

---

### Option 2 — React Context API
**Flutter equivalent:** `InheritedWidget` / `Provider`  
**Verdict:** ⚠️ Use only for simple global data (theme, locale)

- Good for data that rarely changes (auth status, theme)
- Causes performance issues if used for frequently updated state (every context change re-renders all consumers)
- No built-in async support — you'd build that yourself
- Fine for small apps, painful for real feature state

---

### Option 3 — Jotai
**Flutter equivalent:** Riverpod atoms  
**Verdict:** ✅ Very close to Riverpod conceptually

- Atom-based state (exactly like Riverpod atoms)
- Minimal boilerplate
- **Best conceptual match for Riverpod users**
- Slightly less popular than Zustand so fewer examples online

---

### Option 4 — Zustand ✅ (What we use)
**Flutter equivalent:** Riverpod `StateNotifier` / `Notifier`  
**Verdict:** ✅ Recommended — closest feel to Riverpod for Flutter developers

**Why Zustand is the Riverpod of React Native:**

| Riverpod concept | Zustand equivalent |
|---|---|
| `StateNotifierProvider` | `create<Store>()` |
| `ref.watch(provider)` | `useStore()` hook |
| `ref.read(provider.notifier).method()` | `useStore((s) => s.method)()` |
| `state` field | properties in the store |
| `state = newState` | `set({ ...newState })` |
| `AsyncNotifier` | `async` actions inside store |

**Zustand's advantages:**
- **No boilerplate** — one file, define state + actions together (like StateNotifier)
- **Hook-based** — `useHomeStore()` anywhere in a component, just like `ref.watch`
- **Selective re-renders** — subscribe to only what you need, no unnecessary rebuilds
- **Works outside components** — you can call store actions from services, just like `ref.read`
- **TypeScript-first** — full type safety
- **Tiny** — 1KB bundle size

## 7. Flutter Riverpod → React Native Zustand Comparison

### Defining State

**Flutter (Riverpod):**
```dart
// home_state.dart
class HomeState extends Equatable {
  final HomeStatus status;
  final List<HomeEntity> homes;
  final Failure? failure;

  const HomeState({
    this.status = HomeStatus.initial,
    this.homes = const [],
    this.failure,
  });

  HomeState copyWith({...}) => HomeState(...);
}
```

**React Native (Zustand):**
```ts
// home_state.ts
export interface HomeState {
  status: 'idle' | 'loading' | 'success' | 'error';
  homes: HomeEntity[];
  failure?: Failure;
}
```

---

### Defining the Notifier / Store

**Flutter (Riverpod StateNotifier):**
```dart
class HomeNotifier extends StateNotifier<HomeState> {
  final GetHomes _getHomes;
  HomeNotifier(this._getHomes) : super(const HomeState());

  Future<void> fetchHomes() async {
    state = state.copyWith(status: HomeStatus.loading);
    final result = await _getHomes(NoParams());
    result.fold(
      (failure) => state = state.copyWith(status: HomeStatus.error, failure: failure),
      (homes)   => state = state.copyWith(status: HomeStatus.success, homes: homes),
    );
  }
}

final homeProvider = StateNotifierProvider<HomeNotifier, HomeState>((ref) {
  return HomeNotifier(ref.watch(getHomesProvider));
});
```

**React Native (Zustand):**
```ts
// home_store.ts
export const useHomeStore = create<HomeStore>((set) => ({
  status: 'idle',
  homes: [],
  failure: undefined,

  fetchHomes: async () => {
    set({ status: 'loading' });
    const result = await getHomes.call(new NoParams());
    if (isRight(result)) set({ status: 'success', homes: result.value });
    else                  set({ status: 'error',   failure: result.value });
  },
}));
```

---

### Using in a Screen

**Flutter (Riverpod ConsumerWidget):**
```dart
class HomeScreen extends ConsumerWidget {
  @override
  Widget build(BuildContext context, WidgetRef ref) {
    final state = ref.watch(homeProvider);
    final notifier = ref.read(homeProvider.notifier);

    return state.status == HomeStatus.loading
      ? CircularProgressIndicator()
      : ListView.builder(...);
  }
}
```

**React Native (Zustand hook):**
```tsx
const HomeScreen: React.FC = () => {
  const { status, homes, fetchHomes } = useHomeStore();
  //      ↑ like ref.watch(homeProvider)
  //                        ↑ like ref.read(homeProvider.notifier).fetchHomes

  useEffect(() => { fetchHomes(); }, []);

  return status === 'loading'
    ? <GlobalLoader />
    : <FlatList data={homes} />;
};
```

**They are almost identical in concept.** The main difference is syntax, not structure.

---

### Selective Subscription (Avoiding Unnecessary Re-renders)

**Flutter (Riverpod select):**
```dart
final homes = ref.watch(homeProvider.select((s) => s.homes));
```

**React Native (Zustand selector):**
```ts
const homes = useHomeStore((state) => state.homes);
// Component only re-renders when homes array changes
```

## 8. Data Flow — End to End

Here is the complete journey of a "fetch homes" action:

```
User opens HomeScreen
        │
        ▼
[HomeScreen] calls fetchHomes() from useHomeStore
        │
        ▼
[home_store.ts] sets status = 'loading'
```
